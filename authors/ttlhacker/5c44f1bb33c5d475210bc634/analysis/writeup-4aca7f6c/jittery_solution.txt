This is a crackme with several layers to unravel. The summary, though, is that before the
program is run, the machine code that will verify your password doesn't exist; it is instead
compiled on the fly (and in pieces) during program execution. To understand what is going 
on, we will have to figure out (a) how the pieces are compiled, and (b) in what order they 
are compiled. Once we've done that, we'll be able to compile all pieces at once, and fit
them together.

Normally, that would be the end of the story, but two things become apparent when analyzing
the compiled code: first, it is emulating machine code for a (virtual) stack-based
architecture, and second, the password you supply actually modifies the machine code itself
(though, luckily, only slightly). Both of these will have to be figured out in order crack 
this crackme. We will proceed layer by layer.





                                  ======================
                                    Layer 1: The setup
                                  ======================


When the program starts, the first thing it does is create and initialize a memory map which
will eventually hold all the compiled code. We will need to understand the structure of this
mapping, since it's where all the interesting program execution will take place.

The main function for jittery does nothing of interest --- it simply passes execution to a
different function which actually does the setting up and starts execution.

    === main ===
    0xd10:   sub    rsp,0x8
    0xd14:   mov    ecx,0x2
    0xd19:   lea    rdx,[rip+0x206300]        # 0x207020
    0xd20:   mov    esi,0x400
    0xd25:   lea    rdi,[rip+0x2042f4]        # 0x205020
    0xd2c:   call   0x3460                    # call setup function and then run!
    0xd31:   test   rax,rax                   # check if there were unexpected errors
    (the rest of main is omitted)

It is worthwhile to point out the parameters that main passes to the setup function. These
are as follows:

    Parameter 1: a buffer consisting of 0x400 quadwords located at 0x205020
    Parameter 2: the length (0x400) of parameter 1
    Parameter 3: a buffer consisting of two doublewords located at 0x207020
    Parameter 4: the length (2) of parameter 3

While it's not obvious what these parameters are yet, we will see that parameter 1 contains
all the data which will be used to produce machine code for our program. It is therefore
incredibly important --- enough that we will save it off to a separate file (which we will 
call data_buffer) for later use.

    > gdb jittery
    (gdb) dump binary memory data_buffer 0x205020 0x207020

The second parameter is the integer array {10, 7}. It will not change throughout the course
of the program. Believe it or not, this parameter tells the program the order in which to
do its on-the-fly compilations. We will definitely revisit it later.

The setup function (address 0x3460) has three parts of interest to us. First, it creates a
new memory mapping with a call to:

    mmap(NULL, 64*0x400, PROT_EXEC|PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, ...)

Notice the length of the mapping is 64 times the length of our data_buffer. As we will see,
each entry in our data_buffer is going to correspond to a 64-byte block in the mapping. In
fact, the next interesting part of the setup function is where the mapping is intitialized.
Each 64-byte block is initialized separately, in a loop:

    === the initialization loop ===
    0x34d0:   mov    rdx,QWORD PTR [r14]  # r14 iterates through data_buffer
    0x34d3:   mov    rdi,rbx              # rbx iterates through 64-byte blocks of the mmap
    0x34d6:   add    rbx,0x40
    0x34da:   add    r14,0x8
    0x34de:   mov    QWORD PTR [rbx-0x8],rdx    # load the last 8 bytes of mmap block with 
                                                # data from data_buffer
    0x34e2:   call   0x33b0      # this function initializes the first 56 bytes of the 
                                 # current block
    0x34e7:   cmp    rbx,rbp              # check if we've reached the end of the mmap
    0x34ea:   jne    0x34d0               # if not, do another iteration


At the end of the loop, all 64-byte blocks of the mmap have been initialized. The ith block
of mmap now looks as follows (bytes written in hex):

    48 b8 (address of function 0x3210) ff d0 (cc cc ... cc cc) (data_buffer[i])
          |-------- 8 bytes ---------|       |-- 44 bytes ---| |-- 8 bytes ---|

While this may look random, recall that the memory map is meant to be executed (it was 
created with the PROT_EXEC flag, after all). With that in mind, we should be viewing this
block as machine code to be disassembled. When we disassemble it, we get the following:

    === block[i] ===
    movabs   rax, (address of function 0x3210)
    call     rax
    int3            
    ...                    # 44 breakpoints
    int3
    (data_buffer[i])       # not actually code


This completes the initialization of our memory mapping. The only thing remaining to
consider in this function is the code which actually starts the *real* program.

    === the kickoff code ===
    0x34f1:   lea    rsi,[r12+0x40]                 # rsi = address of mmap block[1]
    0x34f6:   lea    rdi,[rsp+0x10]                 # rdi = address of a struct
    0x34fb:   mov    QWORD PTR [rsp+0x10],r12       # struct[0] = address of mmap
    0x3500:   mov    QWORD PTR [rsp+0x18],r15       # struct[1] = address of array {10,7}
    0x3505:   mov    QWORD PTR [rsp+0x20],rax       # struct[2] = length (2) of array {10,7}
    0x350a:   call   0x3390                         # start the real program!

The function 0x3390 takes in two arguments: a struct containing all the information needed
to run the program, and the address of the first block to run. Notice, the first block that
will be run is block[1], not block[0]. This definitely seems weird, but it will make more
sense later.






                            ===================================
                              Layer 2: On-the-fly compilation
                            ===================================


The function 0x3390 really does not do much: essentially it just calls rsi, which holds the
address of block[1]:

    === function 0x3390 ===
    0x3390:   push   rbx
    0x3391:   call   0x3230
    0x3396:   mov    rbx,rdi
    0x3399:   call   rsi                # call block[1]
    0x339b:   call   0x3250
    0x33a0:   mov    rax,rbx
    0x33a3:   pop    rbx
    0x33a4:   ret    

Here's where the fun starts. Recall that block[1] (and in fact all the blocks) start with:

    movabs   rax, (address of function 0x3210)
    call     rax

Thus we immediately jump to function 0x3210, which itself is very simple:

    === function 0x3210 ===
    0x3210:   mov    rdi,rbx   # rdi and rbx point to the struct from before
    0x3213:   pop    rsi       # rsi is now the address of the first "cc" byte in the block
    0x3214:   call   0x3230    # not important
    0x3219:   call   0x32c0    # THIS IS IT! RIGHT HERE, LADIES AND GENTLEMAN!
    0x321e:   call   0x3250    # not important
    0x3223:   jmp    rax       # ??? (We'll come back to this later)

As you can tell, I'm very excited about this function 0x32c0. Why is that? BECAUSE IT'S THE
MOST IMPORTANT FUNCTION IN THE WHOLE PROGRAM. This function takes your current mmap block,
and completely rewrites it. It rewrites it with real code. In other words, this function
"compiles" your block, filling it with legitimate machine instructions. For this reason, I
will call this function compile_block().

We must now dive into compile_block(). First, we will address the following question: how
does compile_block() even know what to do with a given block? After all, each of the blocks
are identical except for in the final 8 bytes. To answer this, consider the following lines 
of code:

    === compile_block ===
    ...                                      
    0x32d8:   movzx  eax,BYTE PTR [rsi+0x2c]  # grab the first byte of data_buffer[i]
    0x32dc:   cmp    al,0x28
    0x32de:   ja     0x330e                   # if it's bigger than 0x28=40, error!
    ...
    0x32e4:   lea    r8,[rip+0x201955]        # 0x204c40 <-- a function table
    ...
    0x3306:   call   QWORD PTR [r8+rax*8]     


This is pretty clear: compile_block looks at the first byte of data_buffer[i] (which, as we
discussed earlier, appears as the last 8 bytes of block[i], making it easy to get!) and uses
it as an index into a function table. This function table consists of 41 functions, each of
which will compile the code block in a different manner.

    CONCLUSION: The first byte of data_buffer[i] determines how block[i] will be compiled.

I certainly won't reverse engineer all 41 of the functions here. But as an example, the 
function given by function_table[3] always produces assembly insructions of the form

    mov   rax, R2
    add   rax, R3
    mov   R1, rax

where here, R1, R2, and R3 can be any general purpose registers. Exactly what R1, R2, and R3
are depends on the bytes of data_buffer[i]. In fact, for each of the functions in the
function table, the bytes of data_buffer[i] give the following information:

    First byte: index into function table.
    Second byte: specifies R1.
    Third byte: specifies R2.
    Fourth byte: specifies R3.
    Bytes 5-8: used as immediate integer data.

In the case of the registers, the bytes give an index into a fixed register list:

    register_list = { r8,  r9, r10, r11, r12, r13, r14, r15,
                     rax, rcx, rdx, rbx, rsp, rbp, rsi, rdi }

Thus, for example, if data_buffer[i] consisted of the eight bytes 03 07 0b 04 00 00 00 00,
then compile_block() would produce the following code:

    mov   rax,rbx
    add   rax,r12
    mov   r15,rax

So now we should have a pretty clear strategy: reverse engineer all 41 of the functions from
the function_table, and then we should be able to compile all the blocks simply by parsing 
the entries of data_buffer. We are not quite ready to do this, however, because we have not
finished going through the compile_block() function. There is still an important step to be
done: linking the blocks together.

After returning from whichever function_table function was called, compile_block() carries
out the following instructions:

    === compile_block, continued ===
    ...
    0x3338:   mov    esi,r12d                   # esi = index of current block within mmap
    0x333b:   mov    rdi,rbp                    # rdi = pointer to the struct from before
    0x333e:   call   0x3270                     # returns index of the "next" block
    0x3343:   mov    ecx,0xffffb848             -----
    0x3348:   mov    rdx,QWORD PTR [rsp]          |
    0x334c:   mov    esi,0xffffe0ff               |
    0x3351:   mov    eax,eax                      |  This code computes the address
    0x3353:   mov    WORD PTR [rsp+0xe],cx        |  of the "next" block and appends
    0x3358:   shl    rax,0x6                      |  two more machine code instructions
    0x335c:   add    rax,QWORD PTR [rbp+0x0]      |  to the current block:
    0x3360:   mov    QWORD PTR [rsp+0x10],rax     |  
    0x3365:   mov    rax,QWORD PTR [rsp+0xe]      |  movabs   rax, (address of "next" block)
    0x336a:   mov    QWORD PTR [rdx],rax          |  jmp      rax
    0x336d:   movzx  eax,WORD PTR [rsp+0x16]      |  
    0x3372:   mov    WORD PTR [rdx+0x8],ax        |
    0x3376:   mov    rax,QWORD PTR [rsp]          |
    0x337a:   mov    WORD PTR [rax+0xa],si      -----
    ...         

We will have to say something about the function 0x3270 which computes the index of the 
"next" block. But before we do, let's just summarize in a picture what compile_block() does
to any given mmap block: 

    === block[i] (before compile_block) ===
    movabs   rax, (address of function 0x3210)
    call     rax
    int3            
    ...                    # 44 breakpoints
    int3
    (data_buffer[i])       # not actually code


    === block[i] (after compile_block) ===
    new instruction        ---
    ...                     |  These came from some function in the function_table
    new instruction        ---
    movabs   rax, (address of "next" block)
    jmp      rax
    int3
    ...                    # any breakpoints that weren't overwritten
    int3
    (data_buffer[i])       # not actually code


Of course, compile_block() just overwrites a block; the new code still hasn't been executed.
When does it get executed? Pretty quickly, actually: compile_block() returns the address of
block[i] in the register rax. After it returns, we're back in function 0x3210:

    === function 0x3210 ===
    0x3210:   mov    rdi,rbx   # rdi and rbx point to the struct from before
    0x3213:   pop    rsi       # rsi is now the address of the first "cc" byte in the block
    0x3214:   call   0x3230    # not important
    0x3219:   call   0x32c0    # compile_block() <--- writes the new code
    0x321e:   call   0x3250    # not important
    0x3223:   jmp    rax       # <--- executes the new code


The only thing left to understand in this layer is the function 0x3270, which computes the
index of the "next" block. In a less challenging crackme, the block following block[i] would
be block[i+1]. But that's not the case here. 

    === function 0x3270 ===
    0x3270:   mov    rcx,QWORD PTR [rdi+0x10]       # length of the array {10, 7}
    0x3274:   xor    eax,eax
    0x3276:   test   rcx,rcx
    0x3279:   je     0x32bf
    0x327b:   mov    r8,QWORD PTR [rdi+0x8]         # address of the array {10, 7}
    0x327f:   xor    edi,edi
    0x3281:   mov    rdx,r8
    0x3284:   lea    rax,[r8+rcx*4]
    0x3288:   nop    DWORD PTR [rax+rax*1+0x0]
(loop start)
    0x3290:   mov    ecx,DWORD PTR [rdx]            # rdx iterates through {10, 7}
    0x3292:   mov    r9d,esi                        # esi = the current block index
    0x3295:   add    rdx,0x4
    0x3299:   sub    ecx,0x1
    0x329c:   shr    r9d,cl
    0x329f:   mov    ecx,r9d
    0x32a2:   and    ecx,0x1                        # grabs the jth bit of esi, j in {10, 7}
    0x32a5:   xor    edi,ecx                        # was the jth bit of esi set?
    0x32a7:   cmp    rax,rdx
    0x32aa:   jne    0x3290 
(loop end)
    0x32ac:   mov    ecx,DWORD PTR [r8]
    0x32af:   mov    eax,0x1
    0x32b4:   add    esi,esi                        # shift current index to the left 1 bit
    0x32b6:   or     edi,esi                        # possibly twiddle the low bit
    0x32b8:   shl    eax,cl
    0x32ba:   sub    eax,0x1
    0x32bd:   and    eax,edi                        # truncate to 10 bits
    0x32bf:   ret    

If you've seen this kind of thing before, you'll recognize what's going on immediately: this
function implements a 10 bit Fibonacci LFSR (wikipedia: linear feedback shift register). The
array {10, 7} is telling the program where the taps are in the register. A very simple 
python version of this function is as follows:

    def step_register(index):
        mask = 0b1001000000                 # bits 10 and 7 are set
        res = (index << 1) & 0x3ff
        if index & mask in [0, mask]:
            return res
        else:
            return res + 1

The choice {10, 7} was not arbitrary. With these taps, if you start at index 1 and keep 
stepping the register, you will see all the indices (except 0) before cycling back to 1. 
The index 0 is special, since step_register(0) is equal to 0. For this reason, if you were
ever to execute block[0], you would get caught in a loop where you just keep executing
block[0] over and over. This is why ttlhacker has us execute block[1] first.






                              ================================
                                Layer 3: The virtual machine
                              ================================


We now have all the ingredients we need to compile all the block ourselves (well, assuming
that you can reverse engineer each of the 41 functions in the function_table --- this was
the most difficult and time-consuming part for me). I wrote a simple disassembler in python 
that takes in the data_buffer (which we saved to a file earlier) and prints out the machine 
code for all the mmap blocks, in the proper order. The code (disassembler.py) is included at
the end of this file, along with its output (disassembler_output.txt). 

While you can easily just read through the assembly (it's only ~1000 lines long), if you
start doing that, you'll see something looks awfully fishy about it. It doesn't look like
assembly you'd get by compiling C code or something. No, it looks like someone compiled down
bytecode for some (stack-based) virtual machine. The very first thing the code does is 
allocate memory for this stack; throughout the code, the register r14 acts as the stack
pointer. But then you start to see code segments that get repeated a lot (a lot!), like:

    mov      r14, r14                                   mov      r14, r14
    movsxd   rax, 0x1                                   movsxd   rax, -0x1
    add      r14, rax                                   add      r14, rax
    movsxd   rax, -0x1                      OR          movsxd   rax, 0x0
    add      rax, r14                                   add      rax, r14
    mov      rcx, r15                                   mov      rax, QWORD PTR [rax*8]
    mov      QWORD PTR [rax*8], rcx                     mov      r15, rax

These code blocks, respectively, implement the instructions  "push r15" and "pop r15" for 
the (virtual) stack.

If you stare at the disassembler output a little longer, you might notice some other
repeated patterns. For example, consider the following code which happens near the start:

    block 0x008: movzxd   r15, 0x020
    block 0x010: jmp      block 0x102
    block 0x020: movsxd   rdi, 0x3
                 ....

Notice that r15 is loaded with the index (0x020) of the block immediately after the jmp.
This feels a lot like a "call" instruction: r15 is loaded with the "return address", and
then execution jumps to a function at block 0x102. This pattern happens repeatedly. And, 
even cooler, at the end of a function, you see the code blocks like the following:

    block 0x12a: jmp      block $r15

In other words, jump back to the return address, which was stored in r15.

Anyway, if this hasn't convinced you that we're looking at the inner workings of a vitural
machine, then keep looking. Here is a summary of some of the rules adhered to by the
machine:

    1) It uses the registers r8, r9, r10, r11, r12, r13, r14, and r15.
    2) r14 is the stack pointer.
    3) r15 always holds the return address when a function is called.
    4) Return values are stored in r12.
    5) When a function is called, it is the caller's responsibility to load r15 with
       the return address
    6) When a function is called, it is the callee's responsibility that save any register
       values on the stack (if necessary). 
    7) Parameters are usually passed in the registers r8, r9, r10, r11

You don't actually have to know these rules to proceed with the crackme, but it's just
really cool....

One thing that should be mentioned, however, are the code blocks which look kind of like:

    block 0x020: movsxd   rdi, 0x3
                 mov      rsi, r14
                 mov      rdx, r14
                 mov      rax, [rel address of function 0x2170]
                 call     rax
                 mov      r13, rax


This function 0x2170 is not part of our mmap code blocks, it's back in the actual program. 
Pseudocode for function 0x2170 would look something like the following:

    long function_2170(long code, long param1, long param2)
    {
        switch(code) {
            case 0:
                putchar(param1);
                return 0;
            case 1:
                return getchar();
            case 2:
                return malloc(param1*8);    // it's a tiny bit more complicated than this
            case 3:
                free(param1);
                return 0;
            case 4:
                return the last 4 bytes of data_buffer[param1];
            case 5:
                return step_register(param1);  // the Fibonacci LFSR previously discussed
            case 6:
                printf("%ld\n", param1);
            case 7:
                return all 8 bytes of data_buffer[param1];
            case 8:
                reset block[param1] to its pre-compiled form, but with 
                      data_buffer[param1] = param2;
                return 0;
            default:
                return 0;
        };
    }


In the context of our virtual machine, I think of calls to function 0x2170 as being kind of
like syscalls. The value of rdi when making a syscall determines which of these 9 system
capabilities gets executed.

                      ===============================================
                        Layer 4: A choose-your-own-adventure ending
                      ===============================================


Most of the VM code is very simple to get through, and the password verification routine
starts off simple: the password must be 56 characters long, must start with 'FLAG{', and 
must end in '}'. This leaves 50 characters between 'FLAG{' and '}', which are checked in 
the functions at blocks 0x33a and 0x1f2. How?

Block 0x33a has a big loop, which will iterate 50 times (once per character). In each loop
iteration, it reads 4 entries of data_buffer, as well as the next password character. Let's
give these names:

    d1 = the first data block
    d2 = the second data block
    d3 = the third data block
    d4 = the fourth data block
     c = the password character

It then calls block 0x1f2 with four parameters:

    Param1 (in  r8) = c - d1
    Param2 (in  r9) = d2
    Param2 (in r10) = d3
    Param4 (in r11) = d4

Notice that the assembly given above for the function 0x1f2 is conspicuously has an invalid
code block. Ordinarily, this would cause a problem, except that immediately before we get to
the invalid code, we change it with a SYSCALL(8). Moreover, Param1 determines *how* the code
block will be changed. 

Let that sink in for a second: the actual code block itself will change depending on the 
character c. You don't just change program flow... you change the program itself. And you 
get choose... what code would you like to put there?

How does this work? The third parameter in the SYSCALL(8) is the new data_buffer entry for
that block, and this parameter is always 0x2010500 | Param1. Since Param1 must be between 3
and 9, the new data_buffer entry will be between 0x2010503 and 0x2010509. Going back to 
layer 2, we know how all the bytes of a data_buffer entry are used to create code. For
example,

    0x2010503 ==>       03 - index into function_table
                        05 - register R1 is r13
                        01 - register R2 is r9
                        02 - register R3 is r10

The only thing you can change is what the index into the function_table is. You are allowed
to choose, 3 through 9. What do those code blocks look like?

    3: mov  r13, r9 + r10
    4: mov  r13, r9 - r10
    5: mov  r13, r9 * r10
    6: mov  r13, -r9
    7: mov  r13, r9 & r10
    8: mov  r13, r9 | r10
    9: mov  r13, r9 ^ r10

They allow you to set r13 as some combination of r9 and r10. Which combination is your
choice. To decide, we should know what is our goal. Immediately following this mutable code
block is the following check:

    cmp     r13, r11
    sete    r12

We want r13 to be equal to r11! Thus for each position in our password, we have to figure 
out (a) which function_table index will make r13 equal to r11, and (b), which character do 
we need in order to choose that function_table index? And that's it! We've reached the end
of this particular rabbit hole!
